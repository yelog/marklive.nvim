# Repository Guidelines

## Project Structure & Module Organization
- Source: `lua/marklive/` (modules: `init.lua`, `config.lua`, `render.lua`, `utils.lua`, `action.lua`).
- Docs: `doc/marklive.nvim.txt` (generated by CI from README; don’t edit directly).
- Tests: `test/*.lua`.
- CI/Config: `.github/workflows/ci.yml`, `.stylua.toml`, `README.md`.

## Build, Test, and Development Commands
- Format (fix): `stylua .`
- Format (check): `stylua --check .`
- Lint: `luacheck lua`  (install: `luarocks install luacheck`).
- Test: `vusted ./test` (install: `luarocks install vusted`; requires LuaJIT/Neovim).
- Local dev: open a Markdown buffer and `:lua require('marklive').setup()` to try changes.

## Coding Style & Naming Conventions
- Lua: 2‑space indent, width 100, prefer single quotes, always call parentheses (see `.stylua.toml`).
- Modules live under `lua/marklive/` and return a table `M`. Use `lower_snake_case` for locals; clear names for public fields/commands.
- Keep user‑facing defaults in `lua/marklive/config.lua`. Avoid editing `doc/` by hand.

## Testing Guidelines
- Framework: vusted (busted syntax). Place specs in `test/` and end filenames with `_spec.lua`.
- Write deterministic tests; avoid relying on user config. Use `describe`/`it` and minimal fixtures.
- Run locally with: `vusted ./test`.

## Commit & Pull Request Guidelines
- Use Conventional Commits: `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`, `ci:`.
- PRs should include: clear summary, motivation, linked issues, and screenshots/GIFs for rendering changes.
- Update README and `lua/marklive/config.lua` when changing behavior, commands, or defaults.

## Docs & CI Notes
- Docs are generated by CI via panvimdoc; edit README to update `doc/marklive.nvim.txt`.
- Requires Neovim ≥ 0.5 and `nvim-treesitter`. Prefer portable Lua; avoid OS‑specific paths.
- CI runs `stylua` and `vusted`; ensure both pass before requesting review.
